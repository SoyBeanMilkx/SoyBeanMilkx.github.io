find_library->find_library_internal()

重定位：实际上就是修正so中调用的外部函数的地址为外部函数在内存中的真正地址。假设一个 so 文件中有一个函数调用 foo()，但 foo() 是在另一个 so 文件中定义的。在编译时，这个函数调用会被编译为一个相对地址（如 call 0x1234）。在加载时，这个相对地址需要被调整为实际的内存地址。

此间小结：

总的来说，so要想被别的模块使用，那它一定是会被映射到内存中的，但我们看见的so文件都是存在磁盘上的，而linker就是完成了这样的一个事情，它把so按照特定的“约定”映射到了内存中，使得我们的app能够使用它。

具体来说，linker主要干了以下几件事情，当然这并不完全，如处理jni环境，与selinux等机制的协同本文不做讨论

1. 加载 ELF 文件（.so 动态库）

  • 使用 mmap 将目标 .so 文件映射到内存中
  • 解析 ELF Header、Program Header 等信息
  • 分配 .bss、.data 等段并初始化

2. 解析依赖的共享库

  • 分析 .dynamic 段中的 DT_NEEDED 字段，递归加载所有依赖 .so 文件
  • 为每个库创建 soinfo 结构（一个代表已加载 .so 的对象，保存名字、基址、符号表等信息）
  • 按照依赖顺序构建 soinfo 链接图，避免重复加载

3. 符号解析和重定位

  • 查找 .dynsym 表中导出的函数或变量符号
  • 对 .rel.dyn、.rel.plt 或 .rela.* 进行 重定位
  • 处理符号冲突、弱符号等情况

4. 处理初始化函数（.init_array/.init_proc）

  • 在所有库加载完成之后，执行 .init_array 段中的构造函数，确保初始化顺序正确

0x04 so加固：

拿360壳举例，它是把主so加密之后塞到了壳so里，壳so作为loader在被原生linker加载之后，loader把壳so解密映射链接重定位……然后调用主so的函数解密释放dex。而我们此时已经实现了loader，为了方便，这里我就不把两个so合并成一个so了，我个人觉得这没有必要，因为主so不管放在哪里，他都是被加密的，你就算看到了这个文件，还是得去分析我的loader才能进行解密，所以我这里采取了一个折中的方案，我把主so藏在了res/mipmap/ic_launcher.webp后面了（这是默认的app logo），因为这样一眼看上去还是图片哈哈哈哈，也不是很容易被发现。流程就是先把主so RC4加密一下，设置个标志（方便后续解密时定位），然后塞到图片里。
